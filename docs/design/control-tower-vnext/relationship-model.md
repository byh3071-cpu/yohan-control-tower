# 관제탑 관계·역링크 모델

## 목적

에이전트, 스킬, 문서, 디자인 산출물, 결정, 일정이 각각 고립된 목록이 되지 않게 한다. 관제탑은 새 정본을 만들지 않고 각 소유 원본의 안정적 식별자와 관계만 읽어 사용자가 “이 결과가 무엇에서 왔고 어디에 쓰이는가”를 추적하게 한다.

## 화면에 보일 핵심 개체

| 개체 | 한 줄 의미 | 기본 소유자 |
| --- | --- | --- |
| 프로젝트 | 결과가 귀속되는 작업 단위 | Brain `projects.yaml` + 프로젝트 Git |
| Goal | 독립 검증 가능한 현재 결과 | 프로젝트 `goals/*.md` |
| 에이전트 역할 | 이번 작업에서 맡은 책임 | 실행 영수증 / 프로젝트 문서 |
| 스킬·도구 | 재사용 가능한 방법과 연결 도구 | Yohan Agent Kit / 설치 환경 |
| 문서 | 기준·참고·결과·피할 패턴·결정 | 프로젝트 Git 또는 Brain |
| 디자인 산출물 | 시안·토큰·명세·검증 이미지 | 소유 프로젝트 Git |
| 결정 | 사람이 선택·거절·보류한 사건 | 프로젝트 결정 로그 |
| 근거 | 주장이나 상태를 뒷받침하는 출처 | 원 소유처 + provenance |
| 일정 | 시간이 정해진 약속·검토·마감 | 현재 Calendar markdown SoT |

## 관계 어휘

관계명은 짧은 한국어 동사로 고정한다.

- `구성한다`: 에이전트 역할 → 디자인 작업팀
- `사용한다`: 작업팀 또는 실행 → 스킬·도구
- `참조한다`: 작업·문서·결정 → 근거 문서
- `만들었다`: 실행 또는 작업팀 → 산출물
- `결정했다`: 사람 결정 → 선택 시안 또는 규칙
- `적용된다`: 기준 문서 → 프로젝트·화면·산출물
- `예정된다`: 일정 → Goal·검토 요청·문서·산출물
- `파생됐다`: 결과물 → 원본 문서·시안
- `대체한다`: 새 결정·문서 → 이전 결정·문서

모든 정방향 관계는 역링크를 만든다. 예를 들어 `design-team이 디자인 명세를 만들었다`는 명세 화면에서 `이 문서를 만든 작업팀: design-team`으로 보인다.

## `design-team` 예시

```text
design-team
├─ 구성한다 → 지휘 · UX · 조사 · 시각 · 기술 · 검토
├─ 사용한다 → product-design · ImageGen
├─ 참조한다 → DesignContext · 조사 · 결정 기록
├─ 만들었다 → 수정 시안 · 디자인 명세
└─ 적용된다 → 관제탑 vNext

사용자
└─ 선택했다 → 3안

Calendar 일정
└─ 예정된다 → 수정 시안 사용자 검토
```

이 구조는 문서에만 존재하는 설명이 아니라 목록 선택 시 검사 열에 1단계 관계로 표시한다. 두 단계 이상 탐색은 별도의 `관계 보기`에서 수행한다.

## 노출 수준

| 수준 | UI 노출 | 예시 |
| --- | --- | --- |
| 공개 요약 | 항상 | 역할명, 한 줄 책임, 상태, 산출물, 문서 링크 |
| 프로젝트 내부 | 권한과 위치가 확인될 때 | 프로젝트 상대경로, Git ref, 검증 기록 |
| 민감 | 노출 금지 | 전체 프롬프트, hidden context, 사고 과정, token, credential, 비공개 원문 |

모델·provider·effort는 역할의 정체성이 아니라 실행 영수증이다. 사용자가 감사나 비용 확인을 요청할 때 보조 정보로 표시한다.

## Design Intelligence 연결

- Brain은 디자인 index, provenance, 관계 schema와 승인 사건을 소유한다.
- 프로젝트 Git은 실제 PNG·영상·시안 원본·문구·명세를 소유한다.
- 관제탑은 둘을 읽어 `탐색 / 비교 / 검토 / 승인 제안`을 제공한다.
- 파일이 ref에 없거나 사람 승인 사건이 유효하지 않으면 관계를 정상으로 표시하지 않는다.
- 현재 확인된 validator 오류는 영향받는 항목에 `근거 확인 필요`로 전달하고 비교·승격 같은 쓰기 행동을 잠근다.

## 검사 열 표현 규칙

- 기본은 그래프가 아니라 두 줄 관계 행이다. 첫 줄에 `출발 개체 + 관계 동사`, 둘째 줄에 `대상 개체 + 상태`를 고정 정렬한다.
- 관계 행 사이에는 최소 16px을 두고 화살표 glyph를 문장 사이에 끼워 넣지 않는다.
- 기본 노출 상한은 구성 역할 6개, 사용 스킬·도구 4개, 참조 문서 4개, 최근 근거 3개다. 상한을 넘으면 처음 항목과 `+N 더 보기`로 접고 전용 목록 또는 관계 보기로 연결한다.
- 역링크 수는 `이 항목을 참조하는 문서 4`처럼 자연어로 표시한다.
- 끊긴 관계는 빨간 그래프가 아니라 `원본 파일을 찾지 못함`, `Git ref에서 확인되지 않음`, `사람 승인 확인 필요`처럼 원인과 영향을 쓴다.
- 날짜는 절대 시각을 기본으로 하고 상대 시간은 보조로만 제공한다.

## 최소 데이터 계약

```ts
type Relation = {
  id: string;
  fromId: string;
  type:
    | "composes"
    | "uses"
    | "references"
    | "produced"
    | "decided"
    | "appliesTo"
    | "scheduledFor"
    | "derivedFrom"
    | "supersedes";
  toId: string;
  sourceRef: string;
  verifiedAt: string | null;
  health: "verified" | "stale" | "missing" | "unknown";
};
```

`scheduledFor`의 source는 CalendarItem이고 target은 Goal·검토 요청·문서·산출물이다. 스킬·에이전트·프로젝트 상세은 이 관계의 역방향 `관련 일정`만 읽는다.

구현 단계에서는 이 타입을 프로젝트의 공용 타입 SoT에 매핑하되, 지금 문서는 production 코드 변경을 승인하지 않는다.
